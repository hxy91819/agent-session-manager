# asm Agent 代码防腐实验方案

## 0. 文档状态与执行入口

- 状态：阶段 A、B 已实施；正式 baseline 和 40 提交历史回放见
  `docs/code-health/`。阶段 C 的 report-only CI 基础设施已准备，观察进度 0/10；
  阶段 D-E 尚未启动，code-health 不阻断合并。
- 最后按代码核对日期：2026-08-07。
- 项目选择：维护者对本项目有最终决策权、持续使用本项目，并确认项目主要由
  Agent 编码。本项目作为代码形态防腐规则的长期验证场。
- 实验对象：生产 Go 代码的重复度、文件长度、函数长度、认知复杂度和圈复杂度。
- 当前探索性数据不是正式 baseline。正式实验必须先固定测量工具版本，再重新
  生成当前版本和历史版本数据。

新会话实施、调整或评估本实验时，按以下顺序执行：

1. 完整阅读仓库根目录 `AGENTS.md` 和本方案；
2. 执行 `git status --short`，保护不属于本任务的现有修改；
3. 核对 `.golangci.yml`、`.pre-commit-config.yaml` 和
   `.github/workflows/ci.yml`，记录已落地阶段；
4. 固定测量工具和规则版本后重新生成 baseline，不把第 2 节的探索性数据直接
   写入门禁；
5. 严格按 A-E 阶段推进，每阶段达到完成标准后再进入下一阶段；
6. 每次阈值变更都保留变更前后的报告、触发率、例外率和修复轮数；
7. 实验结束后形成结论，明确保留、调整或删除哪些规则。

阶段完成标准：

- A：正确性 lint 在 CI 中固定版本运行，当前代码通过；
- B：差异化测量器及其测试已提交，当前和历史 baseline 可重复生成；
- C：至少观察 10 个合并 PR，报告不阻断合并，校准结果已记录；
- D：增量门禁至少运行 20 个合并 PR，所有触发和例外均有结构化记录；
- E：实验报告已提交，并对每项规则作出保留、调整或删除决定。

## 1. 决策与实验假设

测试、代码审查和正确性 lint 主要回答一次变更是否正确。它们不能稳定回答代码
在连续 Agent 修改后是否仍然容易理解和安全修改。本实验把代码形态指标作为
**防腐护栏**，不把它们解释为质量分数。

实验假设：

> 对新增代码执行绝对阈值，对存量代码执行只降不升的棘轮，可以限制复杂度和
> 重复代码的上尾增长，同时不造成明显的机械拆分、例外负担和交付延迟。

需要同时验证相反结果：Agent 可能通过拆出大量微型函数、增加文件跳转或申请
例外来通过门禁。只有复杂度下降而碎片化、修改扩散和维护成本没有明显上升，
实验才算支持该假设。

本项目适合作为验证场，因为它具备：

- 足够大的生产代码和测试代码规模；
- 高频、连续的 Agent 修改历史；
- provider、CLI、TUI、缓存和报告等不同形态的代码；
- 已存在的单元测试、CLI E2E、性能契约和多平台 CI；
- 维护者能够长期观察真实使用体验并最终决定规则取舍。

## 3. 实验范围

### 3.1 首轮纳入

- `cmd/`、`internal/` 和 `tools/` 下的生产 Go 文件；
- 文件物理行数；
- 函数物理行数和 AST 语句数；
- `gocognit` 认知复杂度；
- `gocyclo` 圈复杂度；
- `dupl` token clone groups；
- base revision 与 head revision 之间的指标变化；
- 门禁触发、修复轮数、例外和 CI 耗时。

正式测量器必须在输出中记录每项指标的明确定义和工具版本。指标定义或工具版本
变化时生成新的 baseline series，不能把不兼容数据拼成同一趋势。

### 3.2 首轮只观测

测试文件只生成独立报告，不参与硬门禁。测试表、fixture 和 E2E 场景天然比生产
代码更长，先收集分布后再决定是否需要单独阈值。

以下反作弊指标也只观测：

- 每千行生产代码的函数数量；
- 不超过 5 条语句的函数比例；
- 每个 package 的文件数量；
- 单次变更涉及的文件数量；
- 同一变更中新增 helper 与调用点的比例。

### 3.3 首轮不纳入

- 覆盖率门槛、测试数量和 code review 评分；
- 格式、命名、注释数量和代码风格评分；
- maintainability index 等混合分数；
- package import cycle；
- 自动重构存量超限代码；
- 以缺陷数作为唯一结论。当前样本量不足以快速建立统计显著的缺陷率变化。

## 4. 候选阈值与棘轮规则

阶段 C 根据固定工具生成的数据确认首轮阈值。没有证据要求调整时，阶段 D 使用
以下默认值：

| 指标 | 报告阈值 | 新增代码硬阈值 |
|---|---:|---:|
| 函数长度 | > 50 行 | > 80 行 |
| 函数语句数 | > 30 | > 50 |
| 认知复杂度 | > 15 | > 20 |
| 圈复杂度 | > 10 | > 15 |
| 文件长度 | > 400 行 | 新文件 > 600 行 |
| 重复代码 | >= 50 tokens | 新增 clone group >= 80 tokens |

差异化门禁按以下规则判断：

1. 新函数必须满足全部硬阈值；
2. 存量函数在硬阈值以内时可以变化，但不能跨过硬阈值；
3. 已经超过硬阈值的存量函数可以继续存在，其对应指标必须持平或下降；
4. 超过 600 行的存量文件可以继续存在，但物理行数必须持平或下降；
5. 新增文件不得超过 600 行；
6. head 中新增的 80-token clone group 阻断合并，base 中已有的 clone group
   继续作为债务报告；
7. 函数删除视为改善；函数重命名或移动后无法稳定匹配时按新函数检查；
8. 阈值以内的普通增长不要求同步偿还其他存量债务；
9. 指标下降后，下一次变更以新的较低值为 base，不能重新长回去。

实验开始前不集中重构当前超限代码。存量问题作为自然起点保留，避免清理行为
污染实验，并避免把一次大规模重构的风险错误归因于门禁。

### 4.1 例外

实现 Agent 可以提出例外，不能用通配规则或整文件 `nolint` 自行放行。例外记录
至少包含：

- 文件和稳定 symbol；
- 单个指标及允许上限；
- 不能在当前变更中降低指标的具体原因；
- 替代验证证据；
- 到期日期或到期 PR 数；
- 维护者或独立 clean-context review Agent 的批准记录。

例外属于实验数据。阶段 D 的例外率超过 10% 时，阶段 E 必须判断阈值、测量方法
或代码形态是否不适合，而不是继续累积永久豁免。

## 5. 测量与门禁设计

### 5.1 单一执行入口

新增仓库工具 `go run ./tools/check-code-health` 作为统一入口。工具负责：

- 接收明确的 base revision；
- 对 base 和当前工作区运行同版本测量；
- 以 package、receiver 和 function name 匹配函数；
- 输出当前分布、base/head 差异、告警和硬失败；
- 输出稳定 JSON 供 CI 归档和阶段 E 分析；
- 分别报告生产代码和测试代码；
- 在报告中写入 schema、规则和分析器版本。

阈值配置只有一个 source of truth。pre-commit、CI 和人工运行都调用同一入口，
不在 workflow、shell 命令和文档中各维护一份可执行阈值。

### 5.2 为什么不能只用 `--new-from-rev`

复杂度 linter 通常把诊断定位在函数声明行。Agent 修改函数体并增加分支时，函数
声明行可能不在 diff 中，单独使用 `golangci-lint --new-from-rev` 会漏掉退化。

门禁必须分别测量 base 和 head，再比较同一函数的数值。实现可以在临时 worktree
中测量 base，也可以让分析器直接读取两个 source root；两条路径必须产生相同的
标准化结果。任务创建的临时 worktree 在完成后显式清理，不能影响用户已有
worktree。

### 5.3 重复代码匹配

重复代码比较不能只看告警数量。测量器为 clone group 生成与行号无关的标准化
指纹，并比较 base/head group。删除一个旧 group、同时新增一个不同 group 不能
因为总数相同而被接受。

### 5.4 测量器测试

测试通过临时 fixture 源码验证可观察行为：

- 新函数越过阈值时失败；
- 修改后的存量超限函数持平或下降时通过、增加时失败；
- 阈值以内函数增长但未越界时通过；
- 超大存量文件缩短时通过、继续增长时失败；
- 新增 clone group 被识别，行号移动不产生伪新增；
- 测试文件只报告不阻断；
- malformed source、无效 base revision 和分析器失败返回非零退出码；
- 文本和 JSON 输出对同一结论保持一致。

测试断言门禁契约，不断言内部 AST visitor、命令调用次数或临时目录布局。

## 6. 实验阶段

### 阶段 A：固定基础条件

1. 在 Ubuntu CI 增加固定版本的 `golangci-lint` job；
2. 保持现有正确性 linter 集合不变；
3. 确认本地、CI 和 release 使用兼容的 Go/linter 组合；
4. 记录运行时间和当前输出。

完成条件：同一 commit 在本地和 CI 得到一致结论，当前代码通过，实验期间不同时
扩张普通 lint 规则集合。

### 阶段 B：测量器与历史回放

1. 实现并测试 `tools/check-code-health`；
2. 生成当前生产代码和测试代码报告；
3. 使用同一版本分析最近 30-50 个有生产代码变化的提交；
4. 记录各指标的 P50、P90、P95、最大值和增长次数；
5. 记录函数数/KLOC、微型函数比例、package 文件数和修改扩散；
6. 根据历史分布确认或调整阶段 D 阈值。

完成条件：任一纳入提交都可以重复生成相同结果；历史趋势和原始 JSON 已归档；
阈值调整有数据理由。

### 阶段 C：报告期

至少观察 10 个合并 PR。CI 运行完整测量，但所有代码形态结果使用零退出码，不
阻断合并。每个 PR 记录：

- 新增和恶化的指标；
- Agent 是否主动修正报告；
- 从首次报告到稳定结果的轮数；
- 潜在误报和指标作弊；
- 测量器增加的 CI 时间。

完成条件：10 个 PR 均有结构化记录，且不存在会让大量正常变更无法通过的系统性
误报。

### 阶段 D：增量门禁期

至少观察 20 个合并 PR。候选阈值转为硬门禁，报告阈值继续提供趋势信息。

硬失败后，Agent 应优先降低分支、状态共享、依赖范围或重复规则。拆函数只有在
减少调用者需要同时理解的上下文时才算有效修复。每次失败记录修复轮数；例外按
第 4.1 节处理。

完成条件：20 个 PR 均经过门禁，失败、修复和例外数据完整，没有通过绕过 CI
得到无法解释的样本。

### 阶段 E：复盘与决策

比较历史回放、报告期和门禁期，逐项回答：

- 指标上尾是否停止增长；
- 门禁是否发现了测试和普通 lint 未发现的腐化；
- Agent 是否能在两轮内作出结构性修复；
- 是否出现微型函数、文件碎片和修改扩散；
- 哪些阈值误报最多；
- 哪些指标从未提供独立信号；
- CI 成本和例外成本是否可接受。

每项规则最终只能得到一个明确结论：保留、调整或删除。调整后的规则开启新的
version 和 baseline series，保留旧数据用于比较。

## 7. 评价标准

首轮实验满足以下条件时，认为方案值得保留：

- 门禁期没有新增硬阈值违规和 80-token clone group；
- P95 和最大值相对门禁开始时持平或下降；
- 至少 80% 的门禁失败由 Agent 在两轮内修正；
- 例外率不超过 10%；
- 经维护者或独立 review Agent 复核的误报率不超过 20%；
- 函数数/KLOC、微型函数比例或 package 文件数没有相对历史趋势突增 15% 以上；
- 单个 PR 的修改文件数没有出现无法由需求范围解释的持续上升；
- code-health CI 的 P95 额外耗时不超过 30 秒；
- 后续修复提交和回滚没有相对历史阶段上升。

这些条件用于决策，不组成一个混合总分。某项失败时定位具体规则和副作用，避免
用其他指标的改善抵消问题。

## 8. 计划产物

| 产物 | 用途 |
|---|---|
| 固定版本的 CI lint job | 统一基础正确性门禁 |
| code-health 单一配置 | 保存指标定义、阈值和 schema version |
| `tools/check-code-health` | base/head 测量、比较和退出码 |
| 测量器契约测试 | 锁定差异化门禁行为 |
| 当前与历史 baseline JSON | 提供实验前趋势 |
| PR code-health JSON artifact | 记录报告期和门禁期数据 |
| 实验复盘文档 | 对每项规则作出最终决定 |

实现这些产物时保持产品行为不变。实验工具、配置和 workflow 作为独立 coherent
commit 提交；存量生产代码重构不与测量基础设施合并。

## 9. 首个实施批次

下一次获得实施授权后，只完成阶段 A 和阶段 B 的测量基础设施：

1. 固定并接入 CI lint；
2. 定义 code-health 配置 schema；
3. 先为比较契约添加测试，再实现测量器；
4. 生成当前 baseline；
5. 回放历史提交并提交观察报告；
6. 根据数据确认阶段 C 使用的报告阈值。

该批次不修改生产代码，不清理当前超限函数，也不开启硬门禁。阶段 B 的证据完成
后再决定是否进入 10 个 PR 的报告期。
